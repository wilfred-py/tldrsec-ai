# Context

Domain glossary for tldrsec-ai. The architecture review process ([process/improve-codebase-architecture.md](process/improve-codebase-architecture.md)) reads this file to name modules in the project's own vocabulary rather than generic abstractions.

This file is **lazily populated**. The autonomous review routine adds terms here as it names deepened modules. Hand-edit freely — the routine respects existing entries.

## Format

Each term is a short heading + one paragraph. Cross-link with `[term]` references. Keep entries tight: a term earns a place here when it shows up in module names, function names, or test descriptions.

### Filing
A document filed with the SEC by a public company or insider (10-K, 10-Q, 8-K, Form 4, etc.). The atomic unit of everything tldrsec-ai ingests, summarizes, and emails about.

### Summary
A short, AI-generated digest of one Filing, tuned for retail-investor scanning. The user-facing artifact.

### Subscription
A user's saved interest in a [Filing] type or ticker. Drives which [Summary] payloads they receive in their email.

### Onboarding
The first-run flow that turns a new signup into an engaged subscriber: ticker selection, preview email, account creation, first cached [Summary] delivery.

### X Sentiment
An enrichment of a [Summary] that captures public discussion on X (Twitter) about the ticker over a 7-day window. Direction (bullish/bearish/mixed/neutral/no_signal), shift, confidence, and citation-backed claims. Gated by form importance + a large-cap allowlist (S&P 500) to keep cost and pump-and-dump risk bounded. Runs only for paid-tier callers via the enrichment gate.

### Extractable
A property of a [Filing] meaning the SEC document body, after fetching and cleaning, contains enough structured financial-statement signal for the AI to produce a usable [Summary]. After the NVDA 10-Q fix shipped in this branch, "extractable" has a precise definition: the filing passes both `hasFinancialStatementSignal()` pre-LLM (3 of 5 signals present in the cleaned text: period header, statement title, line items, dollar density, minimum length — see `lib/ai/parsers/financial-content-gate.ts`) AND `hasUsableFinancialHighlights()` post-LLM (at least one `financialHighlights` row passes `isUsableMetricRow`). When the user-facing email says "no extractable financial results," it means one of these gates failed. Filings where `requiresFinancialContent(formType)` is true (10-K, 10-Q, 20-F, 6-K, and amendments) MUST be extractable; failure is treated as a parser bug and the email is not sent. Filings outside that set (Form 4, NT-10-K, etc.) may legitimately be non-extractable and fall through to the minimal-content metadata path.

### SEC Section
A semantic region of a [Filing] — "Risk Factors", "Management Discussion", "Financial Statements", "Business Overview", etc. Canonical type: `SECFilingSection` in `lib/ai/prompts/prompt-types.ts`. Implemented as one deep module (`lib/ai/prompts/context-manager.ts`) behind a five-function interface — `extractSections(cleanedText, formType)` segments cleaned markdown into the canonical buckets, `hasUsableFinancialSection(sections)` is the post-extract gate the Summarize module uses to decide whether to throw AI_INSUFFICIENT_FINANCIAL_SECTION, `buildSectionedPrompt(sections, budget)` assembles a priority-ordered prompt body honoring per-section token budgets, and the `SECTION_TOKEN_BUDGETS` + `SECTION_PRIORITY` tables live alongside. Form-type-aware heading routing (10-Q Item 1 = Financial Statements vs 10-K Item 1 = Business Overview, and 10-Q Part II Item 1 = Legal Proceedings vs 10-Q Part I Item 1 = Financial Statements) is private to the module's `HEADING_TO_SECTION` table — callers never branch on form-type or heading shape. Replaces `lib/parsers/sec-section-extractor.ts`, which split the heading-routing table from the priority-ordered prompt assembly even though it depended on `ExtractedSection` from context-manager and had exactly one production caller (`lib/ai/summarize.ts`); the split was a shallow seam (one adapter, one caller, no leverage). Anything that segments filing text into these buckets, or assigns budgets to them, must reuse `SECFilingSection` — do not define parallel section vocabularies.

### Lifetime Seat
A user who claimed one of the first 25 lifetime seats via a one-time $499 payment. Entitled to all MAX-tier features (see `lib/stripe/plans.ts`) forever, with no recurring subscription. Modeled as a `User.foundingMember: Boolean` flag rather than a new `SubscriptionTier` value, since the entitlement set is identical to MAX. Purchased via a one-time Stripe `Price` (env: `STRIPE_FOUNDING_LIFETIME_PRICE_ID`) under the existing MAX `Product`, not a recurring subscription. Not to be confused with [Subscription] (watchlist interest) or `UserSubscription` (Stripe-side recurring plan record, which Lifetime Seat holders do not have).

### Template Selection
Resolving a [Filing] type to the minimalist email template that renders it, plus a canonical template name for analytics tags. Implemented as one deep module (`lib/email/template-selection.ts`) behind a single `selectFilingTemplate(filingType)` function. Form-type matching is case- and prefix-insensitive (`Form 4`, `FORM 4`, `4` all resolve identically), and unknown types fall back to a generic template so callers never handle a miss. Form 3/4/5 share the insider-trading template. Replaces three drifting copies of the alias→template map that previously lived in `template-registry.ts`, `templates.ts`, and the filings `emailGenerator.ts` — the filings copy had silently regressed to rendering the generic template for DEF 14A, S-1, S-3, 11-K, and 13D filings.

### Email Link Token
An HMAC-signed token embedded in an outbound email link, covering both the feedback links (`userId:summaryId:expiry:signature`, 30-day) and the unsubscribe links (`email:expiry:signature`, 90-day) that ride the `List-Unsubscribe` header. Implemented as one deep module (`lib/email/email-link-tokens.ts`) behind generate/validate pairs that share a single CRON_SECRET-keyed signing layer. Replaces two drifting modules (`feedback-tokens.ts`, `unsubscribe-tokens.ts`) that each carried their own copy of the signing internals AND exported `generateUnsubscribeToken`/`validateUnsubscribeToken` with *incompatible* wire formats — a token minted by one failed validation in the other, so an unsubscribe link's success depended on which entry point (`/unsubscribe` vs `/api/unsubscribe`) it reached. The consolidated `validateUnsubscribeToken` accepts both the canonical and the legacy purpose-marked (`email:unsubscribe:expiry:signature`) format, so links already delivered keep working.

### Historical Context
A prompt enrichment that folds the most recent prior [Summary] entries for a ticker into the current [Filing] prompt so the model can reference continuity (e.g. "Q3 follows the Q2 guidance cut"). Capped at the last 3 summaries, each truncated to 1500 characters to bound token cost. Implemented as private functions inside the Summarize module (`lib/ai/summarize.ts`) — not a separate module — because the only caller is the summarization pipeline itself and the prior extraction-for-testability split offered no leverage. Failures are non-fatal: a Postgres error logs and proceeds without history.

### Why It Matters Guard
The post-parse coercion that enforces a two-state contract on the LLM-emitted `whyItMatters` field of a [Summary]: either a non-empty trimmed string of at least 40 characters that adds context beyond the headline and summary, OR the field is absent. Rejection rules: (1) any 10+ consecutive-word window from `whyItMatters` appears verbatim in `summary` or `headline`; (2) ≥60% of the headline's distinct content words (minus stopwords, ticker, filing-type words) reappear in `whyItMatters`. Implemented as private functions inside the Summarize module (`lib/ai/summarize.ts`) — not a separate module — because the only caller is the summarization pipeline itself and the prior extraction-for-testability split (formerly `lib/ai/parsers/why-it-matters.ts`) offered no leverage. The integration tests in `__tests__/lib/ai/summarize-grounding-wireup.test.ts` exercise the guard through the [Filing Prompt] seam. Same shape as [Historical Context] and ADR-0002.

### Ticker Grounding Guard
The post-parse redaction that scans every prose field of a [Summary] (`whyItMatters`, `headline`, `summary`, `emailSubject`) for ticker symbols or company names that don't match the [Filing]'s actual ticker, and deletes any field that mentions a foreign one. Triggered by a real failure: a fresh JPM S-3 summary's `whyItMatters` read "This $5B shelf provides TSLA flexible, low-cost capital..." — the LLM swapped JPMorgan for Tesla mid-sentence. Shipping the wrong ticker is worse than shipping no analysis, so false positives are tolerated and any suspicious mismatch redacts the field. Detection covers `$TICKER` patterns, bare-word UPPERCASE 2–5-char tokens (minus an acronym allowlist like CEO/USD/SEC), and mega-cap company-name aliases (Tesla→TSLA, Apple→AAPL, etc.). Implemented as private functions inside the Summarize module (`lib/ai/summarize.ts`) — not a separate module — because the only caller is the summarization pipeline itself and the prior extraction-for-testability split (formerly `lib/ai/parsers/ticker-grounding.ts`) offered no leverage. The integration tests in `__tests__/lib/ai/summarize-grounding-wireup.test.ts` exercise the guard through the [Filing Prompt] seam. Skipped silently when the expected ticker is missing or `UNKNOWN`. Has an env kill switch (`DISABLE_TICKER_GROUNDING=1`) for fast rollback. Same shape as [Why It Matters Guard] and [Historical Context], and ADR-0002.

### Numeric Grounding Guard
The post-parse redaction that walks every structured numeric field of a [Summary] (dollar amounts, percentages, large share counts at known paths like `offeringAmount`, `shelfRegistration.totalAuthorized`, `financialHighlights[].value`, `transactions[].shares`, etc.) and confirms each value appears — exactly, in a normalized variant, or within a 5% approximation tolerance — somewhere in the SEC source document. Values without a match are redacted to `null` and a violation is recorded for telemetry. Triggered by the same JPM S-3 failure that anchored the [Ticker Grounding Guard]: the LLM emitted `$5B` for `offeringAmount` when the prospectus authorized `$80B`. Grounds against the SEC source doc only — values backed solely by web-search or [Historical Context] enrichment WILL be redacted because enrichment is for color, not numeric truth. Prose fields are skipped (the [Ticker Grounding Guard] handles those); `*date` paths are skipped because date representations are too varied. Originally-required schema paths (e.g. Form 4 `transactions[].shares`) cannot be nulled without violating the strict-JSON-schema contract — those are preserved and counted under `ai.numeric_grounding_violation_unredactable`. Chunked sources run in warn-only mode (count violations, don't mutate) because values from sibling chunks would otherwise be flagged as fabrications. Implemented as private functions inside the Summarize module (`lib/ai/summarize.ts`) — not a separate module — because the only caller is the summarization pipeline itself and the prior extraction-for-testability split (formerly `lib/ai/parsers/numeric-grounding.ts`) offered no leverage. The integration tests in `__tests__/lib/ai/summarize-grounding-wireup.test.ts` exercise the guard through the [Filing Prompt] seam. Has an env kill switch (`ENRICHMENT_DISABLE_NUMERIC_GROUNDING=1`) for fast rollback. Same shape as [Ticker Grounding Guard], [Why It Matters Guard], and [Historical Context], and ADR-0002.

### Filing Prompt
The system+user+JSON-schema bundle handed to the LLM to summarize one [Filing]. Implemented as one deep module (`lib/ai/prompts/unified-prompts.ts`) behind two functions — `generateFilingPrompt(formType, content, options)` and `getSchemaForFormType(formType)` — plus the `FORM_SCHEMAS` registry. The module dispatches form-type-specific schema and journalist-tone instructions internally; callers (`lib/ai/summarize.ts`, `lib/ai/parsers/simple-parser.ts`, `lib/ai/parsers/numeric-grounding.ts`) never branch on form type. Replaces the legacy dual-prompt system — a `PromptTemplate` base class plus five `Form10KPrompt` / `Form10QPrompt` / `Form8KPrompt` / `FormForm4Prompt` / `GenericFilingPrompt` subclasses (each ~100 LOC of inlined system+user+schema strings) — which had drifted from production for months: zero non-test callers, and the journalist-tone copy lived in two places (the subclasses AND `unified-prompts.ts`) with the unified copy as the only one production actually used. The subclasses' tests asserted on internal substrings of `getSystemPrompt()` output — past the interface, not behaviour — so deleting them removed test mass that wasn't anchored to anything the system shipped. A second drifting copy of the legacy path — the `lib/ai/summarization/` chain (`chunk-processor.ts` calling `prompts/filing-prompts.ts` + `prompts/prompt-templates.ts` via an `EnhancedSummarizationService`) reachable only from `app/api/filings/route.ts` and the orphaned `EnhancedFilingSummary` component / `useEnhancedFilingSummary` hook — was also deleted; its `prompt-types.ts` import of a non-existent `claude-client` module made it un-loadable in production anyway. The deletion concentrates Filing Prompt locality at `unified-prompts.ts` with no parallel path competing for callers.

### Staleness Banner
The amber/red email banner that warns recipients when a [Summary] was delivered significantly after the [Filing]'s original SEC filing date. Renders nothing for filings <7 days old; warning (amber) for 7–29 days; critical (red) at 30+ days. Implemented as one deep module (`components/ui/email/templates/sections/StalenessBanner.tsx`) behind a single `<StalenessBanner filingDate now? />` JSX interface — the daysOld diff, severity threshold, and the inline message string live as private constants inside the component. Replaces a former `lib/validation/staleness-detector.ts` `StalenessDetector` class with `check()` + `formatRelativeTime()` static methods that the banner was the sole production caller of; the split exposed a shallow seam (one adapter, one caller) whose tests asserted on the seam's `result.message` / `result.daysOld` / `result.severity` fields rather than on observable rendered output. The deepened module is verified through `__tests__/email/staleness-banner.test.tsx` against rendered JSX (text plus border-hex retention, per CLAUDE.md #10), including the positional regression test that locks in the banner-above-EmailLeadHeader order across the minimalist templates (10-K, 10-Q, 8-K, Form 4). Same shape as [Why It Matters Guard] / [Historical Context] / ADR-0002.

### Tier Scheduling
How a [Subscription] tier drives the cron pipeline, along two axes that intentionally classify the same tier strings differently. The **priority axis** sets where a job sits in the queue once enqueued (MAX→9, PRO→7, FREE/unknown→5; active trials borrow MAX's 9), with a per-form-type materiality bonus folded in by `getCompositePriority` (8-K most urgent). The **cadence axis** decides whether a user is due for processing and how often (`normalizeTier` buckets both MAX and PRO into one processing frequency — 5 min — while FREE falls to HOBBY's 120 min). Implemented as one deep module (`lib/cron/tier-eligibility.ts`) behind the priority/cadence function set; trial eligibility is delegated to `lib/auth/tier-eligibility.ts` (`isActiveTrial`), the cross-cutting authority shared with auth and summarization. Absorbs the former `tier-priority.ts`, so a maintainer changing tier behaviour reads one place and can see that the two axes disagree on MAX by design.

### Subscription Active
The predicate over a `UserSubscription` row that answers "does this user's recurring subscription cover them right now?" — specifically `isActive=true` AND `currentPeriodEnd` strictly in the future. Implemented as `isSubscriptionActive(sub)` inside the [Tier Scheduling] authority module (`lib/auth/tier-eligibility.ts`), where it composes with the trial-aware `hasActiveAccess` / `isMaxEligible` predicates already living there. Replaces three inlined copies that previously drifted across call sites: `app/api/user/route.ts` and `services/filings/enhanced/subscriptionService.ts` used `new Date() < currentPeriodEnd` while `lib/subscription/tickerSubscriptionInfo.ts` used `currentPeriodEnd >= new Date()`. Each call site also allocated its own `new Date()`, so the three predicates could disagree by milliseconds within a single request. The consolidated predicate uses one `Date.now()` and strict `>` (matches the 2-of-3 majority) — distinct from `hasActiveAccess`, which reads the denormalized `User.subscriptionTier` + trial fields rather than the raw subscription row. Lifetime Seats (ADR-0004) write the sentinel `currentPeriodEnd = 9999-12-31`, which trivially satisfies the predicate.

### Filing Content Verifier
The post-fetch gate that confirms a downloaded SEC document matches the [Filing] metadata the cron pipeline expected — accession number, CIK, form type, company name, optional filing date — before handing the content to AI processing. Implemented as one deep module (`lib/validation/filing-content-verifier.ts`) behind a single `verifyFilingContent(metadata, content)` returning a `ContentVerificationResult` (per-field expected/extracted/matches triples plus a 0–100 `confidence` and required-field error list). Form-type indicator tables (regex patterns for 10-K / 10-Q / 8-K / Form 4) are private to the module; callers never branch on form type. Two production callers: `lib/cron/handlers/fetch-handler.ts` and `lib/cron/handlers/summarize-cached-handler.ts`. Replaces `lib/validation/filing-content-validator.ts` (a 467 LOC `FilingContentValidator` class with its own parallel `ValidationResult` / `ValidationError` taxonomy — zero non-test production callers, and the only "integration" test wired the validator into the verifier in tests but never in production). The deleted validator's NoSuchKey-detection and empty-content checks were already covered by the verifier's `extractedMetadata` + required-field error list flowing through the same single seam. Not to be confused with the Numeric Grounding Guard or Ticker Grounding Guard — those redact LLM output post-summarization; this gate runs pre-summarization on the raw fetched bytes.

### Enrichment Flags
PostHog feature-flag gates that govern the [Filing Prompt] enrichment path: the top-level `why_it_matters_enrichment` kill-switch, per-provider flags (`why_it_matters_counterparty`, `why_it_matters_governance`, `why_it_matters_debt`, `why_it_matters_earnings`, `why_it_matters_capital_return`, `x_sentiment_enrichment`), and the `enable_earnings_mini_deep_dive` cohort gate that toggles the `materialitySignal` field on 10-K/10-Q schemas. Implemented as private functions inside the Summarize module (`lib/ai/summarize.ts`) — `isWhyItMattersEnabled`, `isProviderEnabled`, `isEarningsMiniDeepDiveEnabled` — composed over a single `evaluateEnrichmentFlag(flagKey, accessionNumber)` helper that dynamic-imports `getServerPostHog` so posthog-node's Node-only deps don't leak into client bundles. `accessionNumber` flows through as PostHog's `distinctId` for stable per-filing bucketing. Every gate fails-safe-off — any thrown error or missing PostHog client resolves to `false`, so an outage cannot accidentally enable enrichment. The `ENRICHMENT_FORCE_ENABLE=1` env var is a dev/QA short-circuit; production callers must never set it. Replaces a former `lib/ai/enrichment-flags.ts` (95 LOC, one production caller) whose unit tests asserted on internal flag-name constants (`_internal.TOP_LEVEL_FLAG`, `_internal.PROVIDER_FLAGS.debt_issuance`) past the interface; the integration tests in `__tests__/ai/summarize-enrichment-gate.test.ts` now exercise the gates through the Summarize seam by mocking `posthog-server`. Same shape as [Why It Matters Guard] / [Ticker Grounding Guard] / [Numeric Grounding Guard] / [Historical Context], and ADR-0002.

### SEC EDGAR Access
Production code reaches SEC EDGAR through a small, hand-picked surface in `lib/sec-edgar/`: `client.ts` (`SECEdgarClient` — used by `lib/cron/handlers/fetch-handler.ts` and `fast-poll-handler.ts`), `cik-resolver.ts` (used by `app/api/user/tickers/route.ts`), `ticker-monitoring.ts` (used by the cron discovery / fast-poll handlers and `sec-filing-service.ts`), `environment-aware-fetcher.ts` and `rss-parser.ts` (dependencies of `ticker-monitoring.ts`), `submissions-client.ts` (dependency of `client.ts`), `form-registry.{ts,js}` (kept while `services/filings/` survives), and the shared `types.ts`. There is **no barrel** — every consumer imports the specific file it needs. Replaces an orbital cluster of zero-production-caller modules that the deleted `lib/sec-edgar/index.ts` barrel had been re-exporting: `parsers.ts` (a stand-alone alternative to `filing-extractor.ts` from [Filing Extraction] that nothing chose), `filing-storage.ts` + `test-filing-storage.ts` (a `FilingStorage` class plus a manual-run REPL script — Filings are persisted through Prisma in the cron handlers directly, not through a class), and the entire `ticker-service/` subdirectory (`SECDataClient`, `TickerResolver`, its own `types.ts` — a drifting parallel to `cik-resolver.ts`, the actual production survivor). The `@/lib/sec-edgar` barrel had **zero importers** for over a year. Deletion collapses a 4-candidate hypothetical seam (4 adapters under the barrel, 0 callers) to the small file-level surface production actually exercises.

### Enhanced Fetch
The outbound HTTP wrapper that adds timeout-via-AbortController, status-aware error classification, retry-with-backoff via `executeWithAdaptiveRetry`, and per-request monitoring counters (`network.requests`, `network.request.duration`) on top of `fetch`. Implemented as one deep module (`lib/network/enhanced-fetch.ts`) behind a single `enhancedFetch<T>(url, options)` function returning the parsed body (`responseType`: `'json'` / `'text'` / `'blob'` / `'arrayBuffer'`) and throwing `ApiError` with `ErrorCode` set by HTTP-status mapping. Two production callers — `services/filings/extractors/enhancedDocumentScraper.ts` and `services/filings/enhanced/documentProcessor.ts` — both consume only `enhancedFetch`. Replaces a former 4-helper convenience surface (`get` / `post` / `put` / `del` / `isUrlReachable`) that wrapped `enhancedFetch` with method presets; zero production callers ever imported any of them, and no test asserted on their dispatch. The slim interface keeps the deep retry/timeout/error-classification logic behind one function and forces callers to pass `method` explicitly, which makes the request shape readable at the call site rather than hidden behind a verb-named helper. The [Resilience] retry primitive is the cross-seam dependency; per the seam-discipline rule, no port is exposed because `executeWithAdaptiveRetry` is the only adapter.

### Resilience
Retry-with-backoff and circuit-breaker behaviour applied at every outbound call seam (OpenRouter client, Anthropic client, Resend email, SEC fetch, network helper). Implemented as one deep module pair behind `executeWithRetry` + `executeWithAdaptiveRetry`: `lib/error-handling/retry.ts` carries the fixed/exponential retry loop and the `CircuitBreaker` class; `lib/error-handling/adaptive-retry.ts` adds the latency-aware variant used by `enhanced-claude-client.ts` and `network/enhanced-fetch.ts`. Callers pass a function and a config; the module owns attempt counting, jitter, status-aware retry classification, breaker state machine, and observability hooks. Four parallel shallow implementations previously orbited this concept with **zero non-test callers** — `lib/resilience/circuit-breaker.ts` + `error-handling.ts` + `monitoring.ts` + `retry-utility.ts` (the `lib/resilience/` package), plus the stray `lib/utils/circuitBreaker.ts` — each carrying its own `CircuitBreakerConfig` / `RetryConfig` shape and its own state machine. Their existence forced maintainers to ask "which retry module do I import?" before every change. Deleting them collapses the hypothetical seam (4 candidate adapters, 0 callers) to one real interface, so the surviving canonical module's leverage is unambiguous. A second orbit lived under `lib/db/` — `circuit-breaker.ts`, `connection-warmer.ts`, `connection-manager.ts`, `optimized-connection-manager.ts`, `check-connections.ts`, and `monitoring.ts` (~1037 LOC) — each defining its own `CircuitBreakerConfig` / pool-stats / telemetry shape, none of them imported by production. They were deleted for the same reason: a hypothetical seam (6 candidate adapters, 0 callers) is not a seam. The lone surviving Prisma-flavoured preset `dbRetry` in `lib/db/retry-wrapper.ts` (one production caller, `app/api/user/tickers/route.ts`) keeps its Prisma-specific error-code mapping (`P1001` / `P1008` / `P1017` and `PrismaClientInitializationError`) local to the database seam — distinct enough from the generic HTTP error taxonomy in `executeWithRetry` that the duplication earns its keep. Future Resilience work — bulkheads, hedged requests, deadline propagation — extends `lib/error-handling/` rather than spawning a new sibling package.
