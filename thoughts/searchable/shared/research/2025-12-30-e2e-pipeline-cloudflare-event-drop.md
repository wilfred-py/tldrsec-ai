## Research Question

Document the E2E pipeline architecture focusing on:
1. Cloudflare Worker cron integration
2. Observable events on Cloudflare dashboard
3. Pipeline flow from worker trigger to Vercel endpoints
4. Context: Pipeline was working from ~1:12PM AEST to ~3:12PM AEST on 2025-12-30, then observable events dropped significantly

## Summary

The E2E pipeline uses a **dual-service architecture** with Cloudflare Workers triggering Vercel API endpoints. The Cloudflare Worker runs on three cron schedules (`*/5 * * * *`, `*/10 * * * *`, `0 22 * * *`) and calls different Vercel endpoints based on the schedule:

- **Every 5 minutes**: Main pipeline processing (cleanup locks, tier-aware, discovery, fetch, summarize)
- **Every 10 minutes**: Slack interval summary (detailed verification report)
- **Daily 22:00 UTC (9 AM AEST)**: Daily Slack report

Observable events on the Cloudflare dashboard represent:
1. Cron trigger executions (scheduled events)
2. Worker log entries (`console.log`, `console.error`)
3. HTTP requests made to Vercel endpoints

## Detailed Findings

### Cloudflare Worker Architecture

#### Configuration ([wrangler.toml](cloudflare-cron/wrangler.toml))
- **Worker Name**: `cloudflare-cron`
- **Main Entry**: `index.js`
- **Version**: 2.5.0-stable
- **Cron Schedules**: `["*/5 * * * *", "*/10 * * * *", "0 22 * * *"]`
- **PUBLIC_URL**: `https://tldrsec.app`
- **Required Secret**: `CRON_SECRET` (HMAC authentication)

#### Entry Points ([cloudflare-cron/index.js](cloudflare-cron/index.js))

The worker exports two handlers:

1. **`fetch(request, env, ctx)`** (lines 13-72)
   - Handles HTTP requests to the worker
   - `/health` endpoint returns heartbeat status
   - Tracks `lastHeartbeat` and `heartbeatCount` in memory
   - Returns stale status if no heartbeat in 15 minutes

2. **`scheduled(event, env, ctx)`** (lines 75-120)
   - Handles cron trigger events
   - Routes based on `event.cron` expression:
     - `*/10 * * * *` → `handleIntervalSummary()`
     - `0 22 * * *` → `handleDailyReport()`
     - Default (*/5) → `handlePipelineProcessing()`

### Event Types on Cloudflare Dashboard

Based on the screenshot and code analysis, the observable events are:

1. **Scheduled Event Triggers**
   - Format: `[scheduled-{timestamp}-{randomId}] Scheduled event triggered with cron expression: */10 * * * *`
   - Indicates cron schedule fired

2. **Interval Summary Events**
   - `[interval-summary-{timestamp}] Starting 10-minute interval Slack summary`
   - `[interval-summary-{timestamp}] Interval summary completed successfully in {duration}ms`
   - Generated by `handleIntervalSummary()` (lines 123-177)

3. **Pipeline Processing Events** (most frequent)
   - `[HEARTBEAT] Cron executed at {timestamp} (count: {count})`
   - Step-by-step logs for 5-step pipeline
   - Generated by `handlePipelineProcessing()` (lines 234-895)

### Five-Step Pipeline Processing

The main pipeline (`*/5 * * * *`) executes five sequential steps:

**Step 0: Lock Cleanup** ([index.js:428-475](cloudflare-cron/index.js#L428-L475))
- Endpoint: `/api/cron/cleanup-locks`
- Purpose: Prevent pipeline stalls from stale distributed locks
- Timeout: 30 seconds
- Non-blocking: Continues even if cleanup fails

**Step 1: Queue Discovery Jobs** ([index.js:477-519](cloudflare-cron/index.js#L477-L519))
- Endpoint: `/api/cron/tier-aware`
- Purpose: Queue ASYNC_DISCOVER_FILINGS jobs
- Returns HTTP 202 with job ID
- Blocking: Throws if this step fails

**Step 1.5: Process Discovery Jobs** ([index.js:521-588](cloudflare-cron/index.js#L521-L588))
- Endpoint: `/api/cron/process-filing-queue?jobTypes=ASYNC_DISCOVER_FILINGS`
- Purpose: Process RSS feeds for each user's tickers
- Timeout: 90 seconds (reduced from 270s)
- Max Attempts: 1 (fails fast)
- Non-blocking: Resets circuit breaker on timeout

**Step 2: Process Fetch Jobs** ([index.js:590-630](cloudflare-cron/index.js#L590-L630))
- Endpoint: `/api/cron/process-filing-queue?jobTypes=ASYNC_FETCH_FILING`
- Purpose: Fetch SEC filing content
- Non-blocking: Continues to Step 3 on failure

**Step 3: Process Summarize Jobs** ([index.js:632-674](cloudflare-cron/index.js#L632-L674))
- Endpoint: `/api/cron/process-filing-queue?jobTypes=ASYNC_SUMMARIZE_CACHED`
- Purpose: AI summarization of cached content
- Non-blocking: Jobs retry on next cycle

### Authentication Flow

All requests use HMAC-SHA256 authentication:

1. **Signature Generation** ([index.js:374-398](cloudflare-cron/index.js#L374-L398))
   ```javascript
   const payload = `${timestamp}:${method.toUpperCase()}:${path}`;
   const signature = await crypto.subtle.sign('HMAC', key, encoder.encode(payload));
   ```

2. **Headers Sent** ([index.js:401-426](cloudflare-cron/index.js#L401-L426))
   - `x-hmac-signature`: Hex-encoded HMAC signature
   - `x-hmac-timestamp`: Timestamp used in payload
   - `X-Execution-Id`: Unique execution identifier
   - `X-Cloudflare-Worker`: `tldrsec-cron`

3. **Vercel Validation** ([lib/cron/auth-service.ts:17-106](lib/cron/auth-service.ts#L17-L106))
   - Validates HMAC signature against `CRON_SECRET`
   - Checks timestamp freshness
   - Rate limiting applied

### Circuit Breaker and Rate Limiting

**Circuit Breaker** ([index.js:300-320](cloudflare-cron/index.js#L300-L320))
- States: CLOSED, OPEN, HALF_OPEN
- Opens after 3 consecutive failures
- Blocks requests when OPEN
- Returns `circuit_breaker_open` status

**Rate Limiter** ([index.js:322-345](cloudflare-cron/index.js#L322-L345))
- Window: 60 seconds
- Max requests per window: 30
- Burst limit: 5 requests per 10 seconds
- Global subrequest limit: 1800/minute

## Architecture Documentation

### Event Flow Diagram

```
Cloudflare Worker (*/5 * * * *)
        │
        ├─ Step 0: POST /api/cron/cleanup-locks
        │
        ├─ Step 1: GET /api/cron/tier-aware
        │         └─ Queues ASYNC_DISCOVER_FILINGS job
        │
        ├─ Step 1.5: GET /api/cron/process-filing-queue?jobTypes=ASYNC_DISCOVER_FILINGS
        │         └─ Checks RSS feeds, queues ASYNC_FETCH_FILING jobs
        │
        ├─ Step 2: GET /api/cron/process-filing-queue?jobTypes=ASYNC_FETCH_FILING
        │         └─ Fetches SEC content, queues ASYNC_SUMMARIZE_CACHED jobs
        │
        └─ Step 3: GET /api/cron/process-filing-queue?jobTypes=ASYNC_SUMMARIZE_CACHED
                  └─ AI summarization, sends emails
```

### Timeout Configuration

| Component | Timeout | Notes |
|-----------|---------|-------|
| Cloudflare Worker | 10 minutes | Maximum Cloudflare limit |
| Individual Request | 4.5 minutes | Aligns with Vercel 5-min limit |
| Discovery Step | 90 seconds | Reduced to allow Steps 2-3 |
| Lock Cleanup | 30 seconds | Quick operation |
| Vercel Function | 5 minutes | Max execution time |

### Error Recovery

1. **Lock Cleanup Failure**: Non-blocking, continues pipeline
2. **Discovery Timeout**: Resets circuit breaker, continues to fetch/summarize
3. **Fetch Failure**: Continues to summarize, jobs retry next cycle
4. **Summarize Failure**: Jobs retry on next cycle
5. **Circuit Breaker Open**: Returns early, next trigger attempts recovery
